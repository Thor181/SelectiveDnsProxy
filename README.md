# Selective DNS Proxy (.NET 10)

Локальный DNS-прокси для Windows/Linux с правилами по доменам. Поддерживает DNS over UDP и TCP, статические A/AAAA-ответы, пересылку запросов на отдельный upstream DNS, маршрутизацию HTTP/HTTPS по имени хоста на локальные порты и автоматические SSH-туннели.

## Требования

- .NET 10 SDK для сборки.
- Для порта 53 на Windows обычно требуется запуск терминала от имени администратора.
- В `dnsproxy.json` замените демонстрационные значения на свои. `203.0.113.10` — TEST-NET адрес из примера, он не предназначен для реального сайта.

## Настройка правил (`Rules`)

Секция `Rules` нужна только для чистого DNS-управления, не связанного с туннелями: подмена домена на конкретный IP или отдельный DNS-сервер для зоны. Для хостов из `Routes` она не нужна, можно оставить `"Rules": []`.

Статический IP для точного домена:

```json
{ "Domain": "example.com", "IncludeSubdomains": false, "Address": "192.0.2.25" }
```

Статический IP также для поддоменов:

```json
{ "Domain": "example.com", "IncludeSubdomains": true, "Address": "192.0.2.25" }
```

Использовать отдельный DNS-сервер для домена и его поддоменов:

```json
{ "Domain": "internal.example.com", "IncludeSubdomains": true, "Upstream": "192.168.1.1" }
```

В одном правиле указывайте либо `Address`, либо `Upstream`. Для доменов без совпавшего правила используется `DefaultUpstream`. Самый длинный подходящий домен имеет приоритет.

## Маршрутизация хостов и SSH-туннели (`Routes`)

Схема: клиент спрашивает `drx2.ru` → DNS-прокси отвечает `127.0.0.1` → запрос приходит на локальный порт 80/443 этой же программы → она по имени хоста пересылает соединение в SSH-туннель → SSH-сервер подключается к самому `drx2.ru` (порт 80 или 443) и возвращает ответ.

- **Порт 80 (HTTP):** хост берётся из заголовка `Host`. Если маршрута нет — ответ 404.
- **Порт 443 (HTTPS):** хост берётся из SNI в TLS ClientHello. TLS не терминируется, трафик идёт насквозь, сертификаты не нужны.
- Для хостов из `Routes` DNS сам отвечает на A/AAAA адресом `RouteAddress`; отдельное правило в `Rules` для них не нужно (если правило всё же есть, оно приоритетнее).

Пример:

```json
{
  "ListenAddress": "127.0.0.1",
  "Port": 53,
  "DefaultUpstream": ["1.1.1.1", "8.8.8.8"],
  "Routes": [
    {
      "Host": "rngir-drx-app01.rosneft.ru",
      "SshHost": "user@ssh.example.com",
      "SshKey": "C:\\Users\\user\\.ssh\\id_ed25519"
    },
    { "Host": "local.example", "Target": "127.0.0.1:5003" }
  ],
  "Rules": []
}
```

Поля маршрута:

| Поле | Обязательно | Описание |
|---|---|---|
| `Host` | да | Домен. |
| `IncludeSubdomains` | нет | Распространить маршрут на поддомены. |
| `SshHost` | один из двух | `user@host` или алиас из `~/.ssh/config`. Туннель поднимается автоматически, локальные порты выбираются сами. |
| `Target` | один из двух | Локальный `host:port` без SSH-туннеля (например, туннель, поднятый вручную): на него пересылаются и HTTP, и HTTPS. С `SshHost` не указывается. |
| `SshPort` | нет | Порт SSH-сервера. |
| `SshKey` | нет | Путь к приватному ключу. |
| `SshRemoteHost` | нет | Хост, к которому SSH-сервер подключается по 80/443. По умолчанию — сам `Host`. |

Настройки верхнего уровня:

- `HttpPort` / `HttpsPort` — порты роутера (по умолчанию 80 / 443); `0` отключает слушатель. Роутер включается, только если `Routes` не пуст.
- `RouteAddress` — IP, который DNS отдаёт для хостов из `Routes` (по умолчанию `127.0.0.1`). Он должен указывать на машину, где слушают порты 80/443. Менять нужно только если прокси слушает не на loopback и им пользуются другие устройства сети (например, `ListenAddress` = `192.168.1.5` → `RouteAddress` = `192.168.1.5`).

SSH-туннели:

- Для маршрута запускается `ssh -N -T -L 127.0.0.1:<p1>:<Host>:80 -L 127.0.0.1:<p2>:<Host>:443 <SshHost>` с `ExitOnForwardFailure`, `ServerAliveInterval=30`, `BatchMode=yes`, `StrictHostKeyChecking=accept-new`. Имя `<Host>` резолвится на стороне SSH-сервера.
- При падении `ssh` перезапускается с паузой 1, 2, 4 … до 60 секунд (пауза сбрасывается, если туннель продержался больше минуты). По Ctrl+C все процессы `ssh` завершаются.
- `BatchMode` отключает запрос пароля и passphrase: нужен вход по ключу без passphrase или ключ в `ssh-agent`.
- Нужен установленный OpenSSH-клиент (`ssh` в `PATH`).
- Порты 80 и 443 на Windows могут требовать запуск от администратора и не должны быть заняты другими службами (IIS и т. п.).

## Запуск

Из каталога проекта:

```powershell
dotnet run
```

Чтобы использовать другой конфиг:

```powershell
dotnet run -- .\my-dnsproxy.json
```

Для публикации в отдельный каталог:

```powershell
dotnet publish -c Release -r win-x64 --self-contained false
```

Запускайте опубликованный exe от имени администратора, если используете порт 53. Не запускайте одновременно два экземпляра на одном IP/порту.

## Проверка перед переключением DNS Windows

Сначала проверьте конфигурацию и запуск, затем в другом терминале:

```powershell
nslookup example.com 127.0.0.1
nslookup google.com 127.0.0.1
```

Для правила с IP-адресом первая команда должна вернуть заданный IP. Для обычного домена ответ должен прийти от upstream DNS.

После успешной проверки укажите `127.0.0.1` в настройках IPv4 DNS нужного сетевого адаптера. Если на компьютере включён DNS-over-HTTPS в браузере, браузер может обходить системный DNS; отключите Secure DNS или настройте его соответствующим образом. Для отката верните автоматическое получение DNS или прежние адреса серверов.

## Ограничения текущей версии

- Нет кэша и горячей перезагрузки конфигурации: после изменения JSON перезапустите процесс.
- Правила `Address` отвечают только на запросы A/AAAA; запросы других типов пересылаются обычному или выбранному upstream.
- Это минимальная реализация DNS, не полноценный рекурсивный резолвер. Не открывайте порт 53 в интернет; слушайте только loopback или доверенный локальный интерфейс.
- Для точечного применения только к браузеру проще использовать отдельный DNS-профиль браузера, если он поддерживает нужную схему; системная настройка `127.0.0.1` влияет на все приложения, использующие системный DNS.
